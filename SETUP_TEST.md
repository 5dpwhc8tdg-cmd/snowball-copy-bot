## Что нашёл и исправил по ходу проверки

**1. Слушатель команд умирал через 5,85 часа.** Это лимит job'а GitHub Actions,
но код был общий. На VPS бот молча перестал бы принимать команды через шесть
часов. Теперь лимит только для Actions, на сервере — бесконечно.

**2. Неверный токен не ловился.** Самое опасное: с опечаткой в токене бот
запускался, писал в лог «работает», но **ни одно сообщение не доходило**. Именно
тот сценарий, когда думаешь, что следишь за сделками, а на деле нет.
Добавил `getMe` при старте: теперь процесс отказывается запускаться и прямо
пишет, что токен не принят.

**3. Скрипт не говорил, всё ли на связи.** Добавил проверку журнала после
запуска: если подтверждения «токен принят» нет — выводит предупреждение, а не
бодрое «готово».

**4. Мелочи:** `chown` теперь не валит установку, если пользователь ещё не создан;
пути `APP_DIR`/`UNIT_DIR` вынесены в переменные (нужно было для стенда, полезно и
для нестандартных установок).

## Что скрипт НЕ делает (проверяй сам при установке)

- **Не отключает GitHub Actions.** После переезда обязательно выключи
  `snowball-bot.yml` и `commands.yml` в Actions, иначе дубли по каждой сделке.
- **Не переносит историю «уже виденных» сделок.** Чтобы не получить повторно
  сделки за последние сутки, положи `state/state.json` из репозитория в
  `/opt/snowball-copy-bot/state/` до первого запуска.
- **Не настраивает файрвол.** Для бота достаточно: `ufw allow 22/tcp`,
  `ufw enable`. Все соединения бота — исходящие, входящие порты не нужны.
- **Не ставит обновления безопасности.** Стоит включить `unattended-upgrades`
  или хотя бы раз в месяц `apt upgrade`.

## Что проверить в первые 5 минут после установки

```bash
systemctl status snowball-worker          # active (running)
journalctl -u snowball-worker -n 30       # должно быть «токен принят, бот @имя»
```

И в Telegram: `/status` — должен ответить мгновенно и показать время последней
проверки портфеля.

## Ограничения стенда

Проверял не на настоящем systemd (в песочнице его нет) — юнит прогнал через
`systemd-analyze verify`, который валидирует формат и зависимости. Реальный
запуск службы проверится только на твоём сервере, поэтому первым делом смотри
`systemctl status` и журнал.
